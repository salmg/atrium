§ 01
What it is,
and who it is for

Intro

ATRIUM is an open framework for testing chip payments end to end: the card, the terminal, the link between them, and the authorisation host that finally answers yes or no.

It is not one attack. It is a set of parts you connect. You put it between a card and a terminal, or between a payment switch and an issuer, and from that position you can read everything, change anything, and keep a record of what the other side did about it.

What is in the box:

  • Contact relay on SimTrace2 hardware — a real bank card in a reader on your desk, a real terminal in front of you, and every byte between them under your control.
  • Contactless emulation over PN532 and ACR122U readers, with a complete ISO-DEP driver so the tool speaks the block protocol itself instead of asking the reader to do it.
  • Android relay through NFCGate, when the phone is the more convenient end of the link.
  • An intercept pipeline with seven mutation modes — replace, delete, splice, XOR, flip a bit, prepend, append — plus structural modes that understand the file locator and the data object lists.
  • An ISO 8583 proxy that parses, rewrites, replays and originates authorisation messages, with the message dialect kept in a file rather than in code.
  • Cryptogram verification: recompute the card's ARQC, tell you which copy of the amount it actually covers, and re-sign it if you need the replay to stay valid.
  • Eleven attack templates and five combination playbooks, all declared as YAML.
  • A card memory that remembers what each class of card did, keyed by a hash of its capabilities and holding no cardholder data at all.
  • 787 automated tests, 28,905 lines of Python, no privileged subprocess anywhere in it.
If some of that is new to you

An APDU is a message between a smart card and whatever is talking to it. The terminal sends a command, the card replies, and every chip transaction is a few dozen of those exchanges.

ISO 8583 is the message format banks use to ask each other may this payment go through? It is the language spoken above the terminal, all the way to the bank that issued the card.

ATRIUM works on both, which is the whole point — those two languages describe the same payment, and they can be made to disagree about it.

§ 02
EMV Books 1–4
ISO 8583 DE4, DE49, DE55
EMV tag 9F02, 5F2A

The amount travels twice

When you pay with a chip card, the amount reaches your bank in two different places inside the same message, and each place is protected differently.

One copy is a plain field the network reads. It is called data element 4, and it is the number that gets routed, limit-checked and approved. The other copy is buried inside field 55, which carries the card's own data, and inside that sits tag 9F02 — the figure the card put its signature over.

Two copies. Two protections. And nothing in the protocol suite obliges anyone to compare them.

Why does that matter? Because the card and the issuer never talk to each other directly. Every hop trusts the summary handed to it by the previous one. So when the two copies disagree, the disagreement is settled by whichever component happens to read which field — and that is a behaviour, not a specification.

The same shape shows up all over the transaction. The verification method, the application identity, the currency, the terminal's capabilities: each of them exists in more than one place, protected by more than one mechanism. Most published attacks on chip payments are a version of this. The cryptography held. The parties disagreed about what they were agreeing to.

Here is what it looks like on the wire. One message, one transaction, two numbers.

the network reads DE4 000000012000 routed, limit-checked, approved  →  120.00
the card signed 9F02 000000000001 covered by the cryptogram  →  one cent
The short version

The card signs one number. The network approves a different number. If nobody checks that they match, the signature is protecting something other than the payment you just made.

So the question ATRIUM is built to ask is narrow and testable: when these two copies disagree, does anything downstream notice? Answering it needs a tool at both boundaries, speaking both languages, able to change either copy without breaking the message around it.

§ 03
Why the parts
are worth having
separately

Why a framework, and not another script

Everybody who has tested a payment system has written the same throwaway script. Open the reader, send a SELECT, hardcode the AID, patch one byte in one response, watch what happens. It works, it proves the point, and three months later nobody can run it again — including the person who wrote it.

I have written that script more times than I would like to admit. The difference here is what stayed general.

One parser, two layers

Field 55 of an ISO 8583 message carries ICC data as BER-TLV. That is exactly the encoding a card emits. So the parser that reads a card's response reads field 55 without modification, and every mutation primitive that works on a card response works on field 55 too.

That is one design decision and it is the whole integration between the two halves of the tool. It means you can write an attack once and express it at either layer — change tag 9F02 in a card's answer to the terminal, or change the same tag inside field 55 in the message going to the issuer — using the same vocabulary. Then compare the two results and see which component was actually doing the checking.

What this buys you

A test you can run at the card, then run again one layer up, and read as the same test. Most tooling makes you rewrite it, which means you are comparing two different tests and hoping.

The parts that outlive the experiment

  • The TLV core. Parse, walk, rebuild, repad. Shared by the card side and the host side, and covered by a parity suite that fails the build if the two ever drift apart.
  • The mutation vocabulary. Seven byte-level modes and a handful of structural ones, defined once and applied anywhere a TLV structure appears.
  • The transports. Contact relay, PN532, ACR122U, ISO-DEP, NFCGate. They present the same interface, so a playbook written against one runs against another without an edit.
  • The dialects. How a given payment switch lays out its ISO 8583 message is a YAML file, not a branch in a function. Meeting a new one is a file, not a release.
  • The cryptogram profiles. Which tags a cryptogram covers, in which order, with which padding, is also a file.
  • The test doubles. A fake card, a fake reader, a fake acquirer and a fake issuer, so most of the framework can be exercised on a laptop with nothing plugged into it.

None of those are exciting on their own. Together they are the difference between a demonstration and something you can point at the next card, the next terminal and the next switch without starting over.

Everything interesting is a file

Attack templates, combination playbooks, message dialects and cryptogram compositions are all declarative. That is a deliberate limit on what the code is allowed to know. Payment specifications are confidential, and I do not ship any of them; what I ship is the machinery to express one, so a reader who legitimately holds a specification can encode it themselves.

It also means the interesting part of an engagement is reviewable. You can read what a playbook is going to do before you run it, and hand that file to the vendor along with the finding.

§ 05
ISO/IEC 7816-4
APDU intercept

How the interception works

Commands go down and responses come back up through four hook points. Layer 1 logs and decodes and never modifies anything. Layer 3 does every rewrite.

The order matters, and it is the reason the transcript is worth anything. Layer 1 records the card's genuine response after Layer 3 has already rewritten what the terminal is going to see. So a single transcript holds both halves of any divergence: what the card really said, and what the terminal was told it said.

Layer 3 can also inject a command of its own. The card receives it, the reply is logged, and nothing travels back up to the terminal — so you can ask the card a question in the middle of a live transaction without the terminal ever knowing you did.

Seven response modes are available: replace, delete, splice, XOR, flip a bit, prepend, append. Splice is the one to reach for first. It overwrites a run of bytes at an offset and leaves the length alone, which makes it the safe primitive for probing a value that sits inside a signed template.

XOR and bit-flipping are refused on text fields. On a cardholder name there is no defined answer to which bytes you meant, so the tool declines instead of guessing.

§ 06
ISO/IEC 7816-3 T=0
ISO/IEC 7816-4 §5.2.2

Making a change the receiver will actually read

Changing a value is easy. Changing it so the receiver still evaluates the change is the work.

Every one of these protocols checks the envelope before it reads the letter. Break the envelope and your carefully chosen value gets thrown out by a byte counter that has no opinion about payments at all — and you learn nothing.

Here is the specific trap. The card-layer mutations worth running mostly make the response shorter. Removing a field from CDOL1 decouples the cryptogram from that field. Zeroing the offline-authentication counts in the file locator takes every record out of the signature scope. Deleting the issuer script templates suppresses a PIN unblock.

But on T=0, the byte-oriented contact protocol, the length was agreed before your mutation happened. The card answered 6C 1C, the terminal asked for exactly that many bytes, and now you are handing it three fewer. The terminal restarts the transaction instead of exercising the policy you were trying to reach.

① genuine 70tag 1Alen 26 bytes — CDOL1 still lists 9F02 9000 28 bytes · accepted
② mutated 70 17 23 bytes — the entry is gone 9000 25 bytes · three short, terminal restarts
③ repadded 70 1A 23 bytes — the entry is still gone FF FF FF 28 bytes · accepted, policy evaluated

So ATRIUM appends 0xFF padding inside the outermost template and updates that template's length field. The padding sits outside any inner constructed template, so no parser walking the structure trips over it, and the frame the terminal is counting stays the size it agreed to.

Three bytes of padding

That is the entire mechanism. It is also the difference between being able to run the most interesting class of card-layer test on contact cards and not being able to run it at all — four of the eleven shipped attack templates shrink the response.

The command has to be rebuilt too

A mutation that removes a field from CDOL1 has a second consequence. GENERATE AC is built from that list, so the terminal will now send a command of the old length carrying data laid out for the new one, and the card answers 67 00 — wrong length — which tells you nothing about anything.

ATRIUM reads the mutated CDOL, rebuilds the command around it, and zero-fills any placeholder it cannot derive. The card then evaluates a well-formed request that happens to leave out a field it used to sign. Which is the experiment you wanted.

§ 07
ISO/IEC 14443-4
PN532 target mode
S(WTX)

Contactless: the same problem, backwards

On contactless the constraint flips, and it took me a while to see why.

A PN532 in card-emulation mode returns 253 payload bytes in one frame. Not 262 — that is the chip's buffer, and it is the number everybody quotes. What actually binds is the single length byte in a normal information frame, which caps the whole thing at 255 and leaves 253 once the command header is out of the way. The two are close enough that picking the wrong one gets you a failure deep in the framing code that says nothing about your real problem.

Grow a response past that ceiling and there is nowhere to put the excess, so ATRIUM refuses the mutation rather than emitting a corrupt frame. On contact, a mutation that grows a response is fine and one that shrinks it is the problem. On contactless it is the exact opposite.

There is also a clock running. ISO 14443-4 gives the card a deadline, and a relayed card is slower than a local one by definition — every APDU is a USB round trip, and an injecting rule spends that budget twice.

For a long time I described both of those as facts of the hardware. That was wrong, and writing the ISO-DEP driver is what showed me why.

The lesson

A ceiling belongs to whoever owns the layer that decides it. If you are asking a reader module to do your framing for you, its limits become your limits. Implement the framing yourself and they stop being limits and start being parameters.

With ATRIUM speaking ISO-DEP directly it can chain a long response across frames, because it now owns the framing beneath. And it can send S(WTX), the waiting-time extension, which asks the terminal for more time rather than silently blowing the deadline.

The relay still costs time a local card does not. The difference is that the deadline is now negotiated instead of merely exceeded.

§ 08
ISO/IEC 7816-3 §8.2
EMV Book 1 §8.3
TA3 / TB3

Under the APDUs: getting the card to talk at all

Everything above assumes a card is already talking to a terminal. Getting to that point was the hardest part, and chronologically it came first.

The contact relay is SimTrace2. A bank card sits in a PC/SC reader on the host, simtrace2-remsim forwards each command over USB to a SimTrace2 board, and the board impersonates the card to the terminal all the way down to the electrical layer — supply, clock, reset, and one half-duplex line.

From that platform I inherit the parts that are hard and already correct: the interrupt-driven activation state machine that follows the terminal through the electrical sequence, and the framed USB message plane between host and board. That is a real foundation and I did not rebuild it.

What EMV needs on top of it is a different protocol and a different greeting. SimTrace2's emulation was built for SIM cards, which speak T=0. A large share of bank cards speak only T=1, the block-oriented protocol. And a bank card's ATR — the answer-to-reset, the first thing a card says when it wakes up — encodes a clock rate, a guard time and block parameters it expects to be honoured, with an EMV terminal applying admission rules of its own on top of ISO 7816-3.

So two additions. First, a complete T=1 block layer in the firmware: framing under either error-detection code, the three block types, sequence numbering, chaining in both directions, information-field-size negotiation, and the resynchronise, abort and waiting-extension service blocks. It depends on nothing but the C string library and its own header, which is why it survived a rebase of the whole firmware onto a newer upstream release without a single edit.

Second: the ATR is rewritten in flight

The board runs at one fixed set of transmission parameters. Any interface byte asking the terminal to clock differently is a promise the board cannot keep — forward the clock-rate byte and the terminal clocks four times faster than the board can answer, then sees framing errors instead of a card.

from the card 3BTS F8T0 13TA1 00TB1 FFTC1 01TA2 91TD1 31TD2 FETA3 41TB3 53 4C … 02 01historical 68TCK
to the terminal 3BTS 88T0 — dropped — 81TD1 31TD2 FETA3 45TB3 53 4C … 02 01unchanged E1TCK

Nineteen bytes in, fifteen out. The historical bytes carry the card's identity and pass through untouched, so the terminal still sees the real card.

So the rewrite drops every byte that is an electrical promise, and keeps every byte that is a protocol parameter or an identity.

TA3 and TB3 look like more of the same and are not. They are the information-field size and the block-timing pair. EMV requires TB3 and turns the card down when it is absent, falling back to an ISO default that sits outside the range EMV accepts — every character transmitted perfectly, and the card simply refused.

The historical bytes are the card's identity, and they pass through untouched. The terminal still sees the real card. It just sees it arriving on terms the board can keep.

Why this is the same idea again

Keep what the receiver reads for meaning; correct what the receiver reads as a promise about the physical link. That is exactly the rule from § 06, applied one layer below the APDUs.

§ 09
ISO 8583:1987 / 2003
Dialects as data

The host side, one step at a time

The authorisation boundary was built as a ladder, and each rung gives up a guarantee to gain a capability. I think that ordering is worth showing, because it is easy to jump straight to the last rung and then not be able to trust your own results.

1 · observe
Passive proxy

Bytes forwarded exactly as received, before anything tries to understand them; decoding gets its own copy off the relay path. A wrong dialect degrades to "I could not read that", never to a corrupted link. Pinned by a test that runs it under a deliberately wrong dialect and checks the far side got the original bytes.

2 · rewrite
Mutating proxy

gives up byte-exactness

Rewriting means re-encoding from the decoded form, so a codec bug can now reach the wire. Three rules contain it: a message that did not decode cleanly is never mutated, a message no rule touched is forwarded verbatim, and a failed re-encode forwards the original and says so.

3 · originate
Corpus replay

gives up being an observer

Verbatim resend asks whether there is duplicate detection at all. Freshening rewrites only the volatile routing fields and leaves field 55 untouched, which asks whether the cryptogram is bound to them. Reusing it untouched is the experiment.

4 · verify
Key derivation and cryptogram

needs an issuer master key

Answers which copy the card signed. See § 10.

A dialect is a YAML file: field layout, length encodings, MAC placement, whether the switch is 1987 or 2003. Loading a wrong dialect on purpose is a test in itself — a host that accepts a message in a dialect it does not speak is telling you something.

Replay is where the scoping guard matters most, and § 14 covers it.

§ 10
EMV Book 2
ISO 9797-1 Alg 3

Which copy did the card actually sign?

Up to here the tool can build a disagreement and watch what happens. It cannot yet answer the question underneath it — which of the two amounts is inside the signature?

Answering that needs the cryptography: derive the card's unique key from the issuer master key, recompute the cryptogram over the data a given profile says it covers, and compare. A profile is a YAML file listing the tags, the order and the padding, because those compositions are scheme-confidential and belong to whoever legitimately holds them.

Verification refuses to guess. A cryptogram computed over the wrong data fails identically to a forged one, so a missing tag is reported rather than quietly zero-filled, and the verifier declines to compute at all when its inputs are incomplete. 

$ atrium verify --profile emv-book2 --capture 0f3a.pcap

ARQC MISMATCH  (ATC 015A)
  found     4C8B…
  computed  91D2…
  substituted  9F02   ← DE55 carried no 9F02, so DE4's copy was used
  used         000000012000

→ the card did not sign the amount the switch is authorising

That substitution line is the mechanism worth understanding. When field 55 omits a tag that also exists as a plain data element, the builder may take the 8583 copy — and it records that it did. If the two copies disagree, verification fails and the record tells you which copy was used. Substituting silently would produce a mismatch with no explanation, and you would spend an afternoon blaming your keys.

Re-signing closes the loop for replay. With a valid cryptogram over the new counter and the new amount, an approval no longer tells you the host skipped cryptogram checking. It tells you what that host enforces besides the cryptogram, which is the more interesting answer.

A mismatch is not proof of forgery. A wrong profile, a wrong key or a missing tag produces an identical failure, and the result carries enough context to tell those apart. The self-test checks that derivation, MACing and ARPC generation are self-consistent — and then reports that it has not checked any profile against a scheme's own test vectors, because it has not.

§ 11
Fingerprint · outcomes
No cardholder data

What the tool remembers between sessions

Physical access to a card under authorisation is expensive and usually time-boxed. Throwing away what it told you when the session ends is, I think, the largest inefficiency in how this work is normally done.

So every non-routine status word is recorded together with the instruction byte that caused it. The pair is the unit, because 6985 on GENERATE AC and 6985 on GET PROCESSING OPTIONS mean different things. Routine outcomes are discarded: 9000 and the chaining codes carry no signal and would swamp the store.

The index is a SHA-256 over the sorted application identifiers, the AIP and the decoded capability flags. No PAN, no track data, no expiry, no name.

Why hash the capabilities and not the card

It is a capability class, not a card identity. Two cards from the same product hash identically, so notes from one apply to the next — and the corpus is something you can keep, share with a colleague, or attach to a report without ever holding cardholder data.

Two things read that store. A deterministic recommender ranks up to five next attacks from the profile, the history and the outcome patterns. And an optional LLM agent with eleven tools sits on top of it.

The agent does not invent byte sequences. The search space is explicit before the model sees anything — eleven templates with stated preconditions, a structured card profile, a labelled outcome history — so its job is selection and interpretation rather than protocol synthesis. Every conclusion it reaches is reproducible through the recommender without it. If no provider is configured the platform reports the agent unavailable and carries on.

§ 12
EMV Book 3
Transaction flow

A transaction, exactly as it ran

Captured over native T=1 with the card's rewritten ATR forwarded. Reading the terminal's commands top to bottom is reading the EMV kernel's own logic, which is a good way to learn the flow if it is new to you. 

→ 00 a4 04 00 0e 31 50 41 59 2e 53 59 53 2e 44 44 46 30 31 00   SELECT 1PAY.SYS.DDF01
← 6f 1a 84 0e … a5 08 88 01 01 5f 2d 02 65 6e 90 00            FCI — directory at SFI 1

→ 00 b2 01 0c 00                                               READ RECORD 1, SFI 1
← 70 1b 61 19 4f 07 a0 00 00 00 03 10 10 50 0b … 90 00         AID a0000000031010

→ 00 a4 04 00 07 a0 00 00 00 03 10 10 00                       SELECT the AID
← 6f 20 84 07 … 87 01 01 90 00                                 36 B — chained over 2 blocks

→ 80 a8 00 00 02 83 00 00                                      GET PROCESSING OPTIONS
← 80 06 18 00 08 02 03 00 90 00                                AIP 1800 · AFL 08 02 03 00

→ 00 b2 03 0c 00                                               READ RECORD 3
← 70 7f 5a 08 … 8c 15 … 8d 19 … 96 90 00                       131 B — chained over 5 blocks
                                                               CDOL1 (8c) asks for 29 bytes

→ 80 ae 80 00 1d 00 00 00 00 05 … d2 ba d0 43 00               GENERATE AC, P1=80 — 35 B, one block
← 80 12 80 00 1a ed 4a 80 8f 32 4e 24 42 … 90 00               CID 0x80 = ARQC: go online

→ 80 ae 00 00 27 5a 33 00 00 00 00 05 … 00 00 00               GENERATE AC, P1=00 — 45 B, one block
← 80 12 00 00 1a 5c bf 7f 7c f6 7f d4 a3 … 90 00               CID 0x00 = AAC: declined

The decline is the correct outcome. The card returned a cryptogram asking to go online; with no acquirer to reach, the terminal asked again and the card declined. That is what the same card does inserted directly into the same terminal. Reaching a decision is the success condition here, not the decision itself.

One detail in there is evidence rather than decoration. Both GENERATE AC commands — 35 and 45 bytes — crossed as single blocks. That is only possible if the terminal is acting on the information-field size the rewritten ATR advertises. So the rewrite is not merely tolerated; it is being read and honoured.

It is also why reader-to-card chaining is still untested on hardware: at that advertised size, no ordinary EMV command needs it.

§ 13
Root causes
and their tells

Three bugs, and none of them printed anything

Between a firmware that compiled and a transaction that completed sat three defects. Every one of them was silent. I am writing them down because the shape repeats, and recognising the shape is faster than re-deriving it.

The ATR was refused outright

Symptom: the terminal powers the card, and nothing. No error, no retry worth reading. The card's own ATR was being pushed unchanged, so the terminal was asked to clock four times faster than the board can answer. Every character was transmitted correctly. There was simply no card there as far as the terminal was concerned.

The tell: a clean electrical trace and a dead session. If the physical layer looks perfect and nothing happens, suspect an admission rule, not a wire.

Every response was discarded in the firmware

Symptom: the host log shows the card answering correctly, and the terminal times out anyway. The card-emulation application was still routing responses through the T=0 path, which threw away anything that did not look like a T=0 response. The data made it all the way to the last function and then went in the bin.

The tell: the two ends of your own tool disagree about whether something happened. Always believe the end closer to the wire.

Chunks raced the reader for the line

Symptom: intermittent. Long responses sometimes worked. A response split for USB transport was being written to the half-duplex line as separate chunks, and the second chunk sometimes arrived while the reader was still turning around. Short responses fit in one chunk and never showed the problem.

The tell: failures correlated with size rather than content. That is almost always a framing or timing boundary, not a parsing bug.

Why the tests stayed green through all three

This is the part I would want someone to tell me. The harness fed the block layer synthetic input and checked what came out. It never once checked that the layer had asked the transport to send anything. Three defects, all living in the space between “the layer computed the right answer” and “the answer reached the line”, and every one of them invisible to a suite that only ever inspected the first half.

787 passing tests is a statement about the tests. If your harness never asserts on the boundary you cross, your coverage number is measuring something other than what you think.

§ 14
Setup notes
Scope · safety

Be Aware

The things that will cost you an evening if nobody tells you, and the limits the tool puts on itself.

Before it will run

  • Install pycryptodome. It is in the root requirements.txt, but if it is missing the whole cryptography suite fails on an import error rather than skipping. Thirty one tests fail and none of the messages say install this.
  • Flash the card-emulation application, not the tracing one. On this hardware the tracing build is sniffer-only, and a board that traces beautifully will emulate nothing.
  • Raise the PN532 buffer if you are on the Adafruit library. PN532_PACKBUFFSIZ defaults to 64 and EMV responses are longer than that. Same fix as NFC Copy Cat needed, years later.
  • The relay daemon needs root for raw USB. ATRIUM does not launch it — you run the daemon yourself and the platform finds it by reading /proc. A test walks the module's syntax tree and fails the build if a subprocess call ever reappears.

What it will not do

The card side reads what a card was going to say anyway. The host side originates authorisation messages, which is a different kind of power, so the safety work sits there.

  • The scope allow-list fails closed. No allow-list, no send. Wildcards match one label, so *.test.local will never quietly cover a production subdomain.
  • The PAN check is unconditional and runs whether or not you configured a scope. It warns by default rather than aborting, because a false positive that blocks an authorised engagement is its own kind of failure — but it is loud.
  • Account numbers and track data are masked at capture, not at display. Raw wire bytes are still retained because replay depends on them, so a capture file is cardholder data: it is excluded from version control and can be dropped at the cost of replay.
  • Loopback by default, no privilege escalation, Host-header allow-list against DNS rebinding on the control plane.
  • Scheme specifications are not shipped. Not one. The tool provides the machinery to express a composition; the composition is yours to hold.

For cards, terminals and host links you own or have written permission to test. Findings belong to the parties who can fix them, through coordinated disclosure. That is the only use of this I endorse.

§ 15
Open work

What is still unproven

Listed in the order a fault is likely to surface them. If you are picking something up, start at the top.

GapDetail
waiting-time extension
unreachable		 The T=1 request is implemented and unit-tested, but the half-expiry handler switches only on the T=0 states, so a card slower than the terminal's budget is abandoned rather than granted more time. The contactless side gained exactly this negotiation; the contact side has not.
block timings
borrowed		 The block layer reuses the T=0 waiting-time counter instead of deriving T=1 timings from the ATR.
IFSC disagreement
cosmetic		 The firmware is always initialised with the default 32 and never reads the 254 the host advertises. Harmless — the block buffer absorbs anything a reader may legally send — but the two should agree, especially now that terminals are demonstrably acting on the advertised value.
reader-to-card chaining
untested on hardware		 At the advertised IFSC no ordinary EMV command needs chaining, so the reassembly path has only run in unit tests.
error recovery
untested on hardware		 No EDC error, resynchronise or abort has occurred in a real exchange. The CRC branch has never run outside unit tests either, since LRC is what essentially every real card selects.
ISO-DEP driver
fake chip only		 Chaining and S(WTX) arithmetic are covered against a fake. Whether a given EMV kernel honours a negotiated waiting extension is open.
cryptogram profiles
never validated		 No shipped composition has been checked against a scheme's test vectors, so a verification result is a lead requiring confirmation against material the target's owner supplies.
host verdicts
doubles only		 Replay verdicts have been exercised against test doubles, not certification hosts, so their calibration against real approval behaviour is unmeasured.

The pattern across all of it: the parts that talk to real hardware are the parts with the least coverage, because coverage there costs an authorised engagement rather than an afternoon. That is not an excuse, it is just where the work is.
