Detecting Semantic Divergence Across Payment Layers

Cross-layer, message-level fault injection for EMV cards, terminals, communication links and authorisation hosts

Salvador Mendoza — ATRIUM Project
Artifact: github.com/salmg/elma-pentest

Abstract

Two decades of published attacks on chip payments — PIN bypass, pre-play, contactless CVM downgrade, brand mix-up — share a structure that the tooling built to find them does not reflect: in every case the cryptography held, and what failed was agreement. The card, the terminal and the issuer completed one transaction while holding different beliefs about an authenticated quantity, so the exploitable defect lies in the seam between layers rather than inside any one of them. Testing for such divergence needs an instrument that holds both sides of a seam at once, and existing tools do not: each is bounded by a single protocol layer, treats its target's quirks as code rather than data, and begins every engagement with no memory of the last. This report presents ATRIUM, a message-level fault-injection platform that places a mutating observer at the card–terminal boundary and a second at the acquirer–issuer boundary, joined through one BER‑TLV semantic core spanning both — because ISO 8583 field 55 carries exactly the ICC data a card emits. Four properties are identified and implemented: (i) protocol-faithful mutation, in which transport invariants are re-established after every semantic edit so the device under test reacts to the changed meaning rather than to a malformed frame; (ii) declarative target modelling, in which a switch dialect, an attack, and even the data a cryptogram covers are files rather than code; (iii) a cross-layer consistency check that compares the quantity a switch routes on against the copy the cryptogram covers, and by deriving the card's keys determines which copy was signed; and (iv) a fingerprint-keyed, PAN-free evidence store that makes each session's outcomes reusable by later sessions and other cards. The host half is an escalation ladder — observe, rewrite, originate, verify — in which each rung surrenders a safety property the one below it holds, and the same transport abstraction carries the card half onto the contactless interface. The contact relay runs on SimTrace2, extended here with a T=1 block layer and an in-flight rewrite of the card's answer-to-reset so that it carries a complete EMV transaction on hardware — the same fidelity principle applied one layer below the APDUs. The artifact is 28,905 lines of Python validated by 787 automated tests; empirical evaluation against a card, terminal and host population under authorised engagement is stated as future work rather than claimed here.

Index terms — EMV, ISO 8583, smart cards, message-level fault injection, man-in-the-middle, protocol testing, payment security, DE55, TLV, LLM agents.

Authorised use only.  ATRIUM is a research instrument for cards, terminals and host links that the operator owns or has written permission to test. Nothing in this report describes a technique for obtaining value from a payment instrument, and the platform ships no scheme-confidential interface specification. See §11.

1Introduction

A chip payment is a negotiation among parties who do not trust each other and cannot see each other. The card holds keys and a policy; the terminal holds the merchant's risk appetite and the cardholder's physical presence; the issuer holds the account and the final word. The protocols that connect them — EMV over ISO/IEC 7816 on the contact interface, ISO 8583 across the acquiring network — exist to make those three parties agree on one description of one transaction, and then to bind that description cryptographically.

The published record of attacks on this system is remarkably consistent about where it breaks. The 2010 PIN-bypass attack against Chip and PIN did not recover a key: it let the terminal believe a PIN had been verified while the card believed no cardholder verification had occurred, and the issuer received an authorisation whose cryptogram was silent on the difference [1]. Pre-play attacks exploited a terminal's unpredictable number being predictable, so a cryptogram computed today authenticated a transaction tomorrow [2, 3]. The 2021 contactless PIN bypass rewrote a single terminal-facing flag so the terminal skipped verification the card still considered mandatory [4]. The card-brand mix-up attack ran one scheme's kernel against another scheme's card, so each party applied rules the other had not agreed to [5]. Currency and amount manipulation on contactless produced authorisations for values the cardholder never saw [6].

In each case the primitives held. What failed was that two participants finished the transaction holding different beliefs about the same authenticated quantity, and the mechanism intended to bind those beliefs — the application cryptogram — covered only one copy. We call this a semantic divergence. It accounts for a large share of the published attacks on deployed payment systems, which are otherwise easy to read as unrelated bugs.

The instruments available for finding divergence do not match its shape. A logic-level sniffer sees the card–terminal exchange but has nothing to say about what the acquirer forwards. A host test harness speaks ISO 8583 to a switch but has never seen the card that produced the field it carries. A grammar fuzzer will happily corrupt a length prefix, which tells you how a parser handles garbage but nothing about how a policy engine handles a well-formed lie. And every one of them starts each engagement with an empty notebook: what a card did last month, or what a similar card did on another operator's bench, is not available to inform what to try next.

1.1  Thesis

The claim is this:

Thesis

Payment-system security testing should be organised around agreement between layers as the property under test. An instrument that can test for it needs four properties at once — protocol-faithful mutation, declarative target modelling, a shared semantic core across layers, and persistent evidence keyed to a non-identifying card fingerprint. No property is sufficient alone, and the fourth is what lets results accumulate across sessions instead of being discarded with each one.

The remainder of the report develops that claim. §2 fixes the protocol background and names the points at which beliefs are formed. §3 states the problem and derives the four properties. §4 positions the work against existing tooling. §5 gives the architecture. §6–§9 present the technical contributions in the order the four properties demand. §10 works four end-to-end examples. §11 covers safety posture and ethics, §12 evaluation, §13 limitations and roadmap.

2Background: where beliefs are formed

A contact EMV transaction is a short conversation of application protocol data units (APDUs). Each step deposits a belief in one of the participants, and each belief is a candidate for divergence.

2.1  The card–terminal exchange

Selection. The terminal reads the payment system directory (1PAY.SYS.DDF01 on contact, 2PAY.SYS.DDF01 on contactless) or probes a list of application identifiers, and selects one. The card answers with a File Control Information template that includes the Processing Options Data Object List (PDOL) — a declaration of exactly which terminal-supplied values the card wants, and in what order and length.

Initiation. The terminal packs those values — amount, currency, country, terminal capabilities, an unpredictable number, a terminal transaction qualifier on contactless — into a GET PROCESSING OPTIONS command. The card replies with the Application Interchange Profile (AIP), a bitmap of what authentication and verification it supports, and the Application File Locator (AFL), a map of which records to read and which of them fall inside the offline data authentication signature.

Reading. The terminal reads those records: the CVM list defining which cardholder verification methods apply under which conditions, the issuer action codes, certificates, and the CDOLs — the object lists governing what the terminal must supply when it asks for a cryptogram.

Decision. The terminal performs offline data authentication, cardholder verification and risk management, forms its view of the transaction, packs the CDOL1 fields, and issues GENERATE AC. The card returns an application cryptogram computed over the values it was given.

The critical property: the cryptogram covers what the CDOL said it would cover, and nothing else.

If the amount is not in CDOL1, the cryptogram is not bound to the amount. If the CVM results byte is not in CDOL1, the cryptogram carries no evidence of how the cardholder was verified. Both facts are entirely conformant; both are decided by data the terminal read from the card moments earlier.

2.2  The authorisation message

Above that exchange, the acquirer builds an ISO 8583 authorisation request. Data element 4 carries the transaction amount that the switch routes, limits and authorises on. Data element 55 carries ICC data as BER‑TLV — including tag 9F02, the amount the card was told about and the cryptogram was computed over.

The same quantity therefore travels twice, in two encodings, protected by two different mechanisms: DE4 by the network's integrity controls, 9F02 by the cryptogram. Nothing in the protocol suite forces a downstream system to compare them.

2.3  The transport that carries the lie

One detail of ISO/IEC 7816‑3 T=0 dominates the engineering of any contact-side mutation, and is the reason §6.1 exists. In T=0 the terminal must state in advance how many bytes it expects. When it asks for more or fewer than the card has, the card answers 6C XX — "re-issue with exactly XX" — and the terminal complies. The length is therefore negotiated and then fixed before the data arrives.

A mutation that deletes a tag, truncates a locator or substitutes a shorter value changes that length after the negotiation has concluded. The terminal does not evaluate the changed policy; it observes a short frame and restarts the transaction. The tester learns nothing about the device under test except that it can count.

3Problem statement

Let a transaction be described by a set of quantities q₁…qₙ — amount, currency, verification method, application identity, terminal capability. Each participant P ends the transaction holding a belief bₚ(qᵢ). A protection mechanism binds some subset of those beliefs cryptographically.

A semantic divergence exists when two participants complete a transaction with bA(qᵢ) ≠ bB(qᵢ) for some qᵢ that at least one of them treats as authoritative, and no participant is positioned to detect the difference. The exploitability question is not whether divergence can be induced — a man in the middle can always induce it — but whether any deployed component notices.

That framing has a direct consequence for tooling. To test a divergence you must be able to (a) induce it precisely at one boundary, and (b) observe the consequence at another. A single-layer instrument can do the first, never the second.

3.1  Four required properties

P1 — Protocol-faithful mutation

A mutation must change meaning while preserving every transport invariant the receiver checks before it reaches its policy logic: frame length, structural well-formedness, length-prefix arithmetic, object-list arity. Otherwise the receiver rejects the frame and the test measures the parser rather than the policy. This is not a matter of degree: on T=0 contact, a three-byte length discrepancy aborts the transaction before the CVM decision is ever taken.

Three techniques share the word fault and target different things. A fuzzer emits malformed input to break a parser. Glitching — voltage, clock or laser — perturbs a chip's physical execution to skip an instruction, and in the smart-card literature is what fault injection most often means. This work does neither. It performs message-level fault injection, known in the dependability literature as interface fault injection: every injected fault is a well-formed message carrying a wrong value, delivered at a protocol boundary, so what is exercised is the receiver's policy rather than its parser or its silicon. No result in this report depends on physical access to a chip beyond holding the card in a reader.

P2 — Declarative target modelling

"ISO 8583" names a family, not a protocol; deployments differ on at least eight independent axes (Table II). "EMV" is likewise parameterised per card. Any tool that encodes a target's choices in code is single-target and disposable, and — worse for research — its results are not portable between engagements. Targets must be described by data the operator can author and version.

P3 — A shared semantic core across layers

The cross-layer check is only cheap because DE55 is BER‑TLV, the same encoding the card emits. If the two layers are modelled by two independent parsers, every comparison becomes a translation with its own bugs. One core, used by both, makes the check a few lines of comparison — and makes divergence between the two implementations a testable property in its own right.

P4 — Persistent, non-identifying evidence

A card's response to a mutation is expensive evidence: it requires physical access, an authorised engagement, and time. Discarding it at the end of a session is the largest single inefficiency in current practice. Evidence must persist, keyed so that it generalises to similar cards rather than only the exact specimen — and keyed by something that is not cardholder data, so that the resulting corpus is not a liability.

3.2  Evaluation model

ATRIUM assumes a card the operator is authorised to test, a terminal or host under the same authorisation, and an operator who may position hardware or a proxy on either boundary. The adversary being modelled is a merchant-side or network-position attacker; the adversary being defended against in the tool's own design is anyone who reaches the operator's control plane (§11).

The card-layer half additionally requires the genuine card, physically, in a reader under the operator's control — it manipulates a live session and cannot fabricate one. The host layer is not bounded that way and it would be wrong to imply otherwise: replay (§7.3, rung 3) originates authorisation messages from a captured corpus with no card and no acquirer present. What bounds it instead is the scoping guard — a target allow-list it will not transmit outside, and a cardholder-data policy that treats a live account number as a signal the link is pointed at production (§11.2). That is a weaker bound than physics, and it is why the ladder's most active rung carries the most explicit constraints.

4Related work and the tooling gap

Attack literature. The divergence framing is a synthesis of results rather than a new observation about any one of them. Murdoch et al. [1] demonstrated terminal/card disagreement over cardholder verification; Bond et al. [3] and Roland and Langer [2] showed pre-play and downgrade paths in which a cryptogram authenticates a transaction other than the one presented; Basin et al. established both the contactless PIN bypass [4] and the brand mix-up [5] by formal analysis with Tamarin, and Emms et al. [6] showed currency-scoped divergence. De Ruiter and Poll [7] gave an early formal treatment of the suite. What this body of work does not supply is an instrument: each result was obtained with bespoke apparatus, and the apparatus rarely outlived the paper.

Formal verification proves properties of a model. It is complementary and, in our view, upstream: a model tells you which divergences could matter; only an instrument on real hardware tells you which deployed component actually notices. ATRIUM is explicitly the second thing.

Capture and relay tooling. Contact and contactless sniffers, virtual-card bridges [9] and relay boards solve the physical problem of getting between two parties. The contact side of this work runs on SimTrace2 [10]: its hardware, its card-emulation application, and its host relay tool are the foundation everything in §5 and §6 sits on. SimTrace2 supplies the electrical activation state machine, the USB message plane between host and board, and byte-oriented card emulation, all of it proven in the SIM-relay role it was built for. Carrying an EMV transaction additionally requires the block-oriented protocol and an answer-to-reset an EMV terminal will admit; that extension is described in §6.4 and reported in full in the companion note [15].

Fuzzing. Grammar-based and coverage-guided fuzzers excel at finding memory-safety and parser defects. They are structurally poor at policy defects: a fuzzer's success criterion is a crash or a coverage delta, whereas a divergence produces a perfectly successful transaction with the wrong meaning. P1 inverts the fuzzing objective — never malform, always mean something different.

Host-side harnesses. Acquirer and issuer simulators exist commercially and in open source, and are generally built around a single institution's interface specification. They test conformance to a spec, not disagreement with the layer below, and they have no view of the card.

5Architecture

ATRIUM is two halves that share a semantic core and nothing else. The card half is a man-in-the-middle between a terminal and a card — on the contact interface through a SimTrace2 board whose card-emulation firmware and host tool this work extends (§6.4), on the contactless interface through an emulating reader: the terminal believes it is talking to a card, the card believes it is talking to a terminal, and every APDU pair passes through a pipeline that logs, decodes, fingerprints and — when armed — rewrites. The host half is a full instrument for the ISO 8583 authorisation link above it — proxy, capture, mutation, replay and cryptography — built as the escalation ladder of §7.3. Neither half imports the other's hardware dependencies; the host package runs on a machine with no reader attached, and its dependency file is short enough to check.

5.1  The card-side pipeline

Commands descend and responses ascend through four hook points, shown in Fig. 2. Layer 1 (emv_logger.py, 1,568 lines) performs structured logging with full TLV decoding and never modifies. Layer 3 (mutation_engine.py, 1,833 lines) performs every rewrite. The separation matters for evidence quality: the log records what the card actually said, not what the terminal was told it said, so a session transcript contains both sides of any divergence the operator induced.

Three orthogonal mutation families are available. Command-side mutations rewrite the PDOL-derived data in GET PROCESSING OPTIONS, unpacking the terminal's buffer against the PDOL layout captured from the preceding FCI, substituting fields, and re-packing. Response-side mutations locate tags in the card's answer and apply one of seven modes — replace, delete, splice, xor, flip_bit, prepend, append — plus structural modes specific to the AFL (skip_signed, truncate, remove_sfi, extend) and to the CDOLs (remove_field, truncate). Injection fires additional APDUs to the card at defined flow points; responses are logged and never forwarded, so the terminal's view of the transaction is unchanged while the operator obtains data the terminal never requested.

5.2  One interface, five card sources

All card I/O passes through a single CardTransport interface (Fig. 3), and every layer above it — the fingerprinter, the mutation engine, the logger, the agent — is written against that interface alone. What sits behind it has grown to five backends, none of which the upper layers can distinguish. A local transport drives a physical card through a PC/SC reader. A remote transport reaches a card in another network over the pinned TLS link of §9, so a card in one jurisdiction can be driven by a rig in another under a single authorised engagement. A recorded transport answers APDUs from a capture file, which needs no card at all and is what lets the whole stack — and most of its test suite — run with no hardware present. A contactless transport drives a card in an ACR122U's radio field. And an Android transport reaches a card held in a phone's field over NFCGate, so the reader an operator already owns becomes a card source anywhere the phone can reach the session server — at the cost of a network hop in a budget that was already tight, and of a server that authenticates nobody and therefore belongs on loopback.

The abstraction that once bought only location independence now also buys interface independence, and — through the emulator of §9 — direction independence: the same pipeline that mutates a card's answers to a terminal can instead present an emulated card to a terminal and mutate a real card's answers on their way out. A recorded capture standing in for that real card closes the loop, letting an operator see exactly what a terminal asks for with nothing physical on the bench but the emulating reader.

Naming the readers. That flexibility created an operational trap worth a mechanism of its own. Readers were once addressed by an opaque PC/SC index, which is stable until the virtual card bridge is running — at which point the virtual reader, ATRIUM's own output side, usually lands at index 0. Defaulting to it is always wrong on a working rig and produces an error that reads like a card fault rather than a wiring mistake. Reader discovery is therefore centralised: each reader is classified as virtual, contact or contactless from its PC/SC name — matching the interface marker (PICC/ICC) on a word boundary, since a dual-interface reader exposes both slots under one model name — so nothing downstream has to guess which index is the card side. A reader can still be selected by index, but it can also be identified physically by blinking its light through the same ACR122U escape channel the emulator uses, and by its position on the USB tree.

5.3  Control plane

A FastAPI application serves a six-stage operator console — hardware, session, fingerprint, attack, agent, results — over WebSocket-streamed APDU and agent events. The console is a convenience; every stage has a command-line equivalent, and the platform's guarantees do not depend on the browser being present.

6Protocol-faithful mutation (P1)

This section presents the two mechanisms that distinguish message-level fault injection from mere corruption on the contact interface. Both exist because a semantic edit has structural consequences that the receiver checks before it reaches any decision logic.

6.1  T=0 length preservation

Consider the most interesting mutations available at the card layer. Removing a field from CDOL1 decouples the cryptogram from that field. Zeroing the offline-authentication record counts in the AFL removes every record from the signature scope. Truncating the AFL suppresses the records that carry the CVM list. Deleting tag 8D prevents the second GENERATE AC. Deleting issuer script templates suppresses a PIN unblock.

Every one of them makes the response shorter. On T=0 that is fatal to the experiment, for the reason given in §2.3: the length was negotiated via 6C XX before the mutation happened, and a short frame restarts the transaction rather than exercising the policy.

ATRIUM restores the negotiated length after every shrinking edit (Fig. 4). The mechanism is narrow: it appends ISO/IEC 7816‑4 padding bytes (0xFF) inside the outermost BER‑TLV template and rewrites that template's length field to match, so the frame the terminal receives is byte-for-byte the length it asked for, structurally valid, and semantically identical to the mutated content — the padding lies outside every inner tag and is skipped by any conformant TLV walk.

Correctness is guarded rather than assumed. The routine decodes the outer tag (including multi-byte tags), decodes the length in short, 0x81 and 0x82 forms, and verifies that the declared inner length equals the actual remaining bytes before touching anything. If any check fails it logs and returns the response unmodified — a failed pad is a lost experiment, whereas a wrong pad is a corrupted one that could be misread as a device defect.

Why this is the enabling contribution

Without length preservation, the mutations that test cryptographic binding — the class that produced the most consequential published attacks — cannot be run at all on contact cards. Of the eleven attack templates ATRIUM ships, four shrink the response and are untestable without it. It is a small routine that changes what the platform is capable of asking.

6.2  DOL-aware command reconstruction

The second mechanism handles a subtler asymmetry. When ATRIUM removes a field from CDOL1 in a READ RECORD response, the terminal reads the shortened list and packs GENERATE AC accordingly — one field lighter. The card, however, was never told: it still expects the original layout and will parse the buffer against it, mis-aligning every subsequent field.

A card that validates the command length against its own CDOL1 answers 67 00 — wrong length — and the transaction dies before any cryptogram is computed. The engine therefore retains both layouts for the session and reconstructs the command before forwarding: it walks the original layout, copies through every field the terminal did supply, and inserts a zero-filled placeholder of the declared width wherever a field was stripped. The card receives a well-formed request in exactly the layout it declared; the terminal believes it supplied a complete one; the cryptogram is computed over zeros for the removed field.

That is the divergence, constructed and observable: the transaction succeeds, the terminal prints the real amount, and the cryptogram is not bound to it. Whether that matters is then a question about the issuer, which is what the host layer (§7) is for.

6.3  The contactless mirror: who owns the framing layer

Extending the mutation pipeline to the contactless interface exposed the same class of problem with the sign flipped, and the contrast is instructive about what protocol-faithful mutation actually requires. On contact T=0, the hazard is a response that has become too short for a length negotiated in advance, and §6.1 answers it by growing the frame back with padding that carries no meaning. On the contactless interface driven through the ACR122U's PN532, there is no advance length negotiation to satisfy — but the chip carries at most 262 bytes in one exchange, so the hazard is the opposite: a mutation that makes a response too long — a replaced tag with a longer value, an append, a splice past the boundary — cannot be sent at all.

When the ceiling is genuinely fixed there is no way to grow past it, so the mechanism declines (Fig. 5): an oversized mutated response is dropped in favour of the card's own bytes, the exchange is relayed unmutated, and a counter records how often it happened. The operator reads "that rule does not fit contactless" from the trace rather than watching the radio link drop into a timeout with nothing to diagnose. This is the same value judgement as the contact side — a failed mutation is a lost experiment, a corrupted link is a lost afternoon.

But the ceiling is not a law of the interface; it is a consequence of who owns the block layer. Left to itself the PN532 performs ISO/IEC 14443-4 on the platform's behalf, which is why the emulator deals in whole APDUs — and why one response must fit one frame, why the frame waiting time is the firmware's choice, and why a relay that outruns that budget is dropped with nothing said. Taking that layer over reverses all three at once: the platform answers RATS with an ATS it composed, so the terminal's waiting budget is one it chose; it can send S(WTX) to ask for more time while the relayed card is still being waited on, which is the mechanism the standard provides for exactly this situation; and a long response goes out as several chained blocks rather than being refused, which retires the ceiling outright.

That is offered as a second driver rather than a replacement, and the reason is the ladder of §7.3 read at a different layer. The chip-managed path is the proven one and remains the default; owning the block layer buys capability by taking on every detail the firmware was handling correctly. The generalisation is that protocol-faithful mutation is bounded by the lowest layer the tester controls: on contact the platform owns the TLV template and can therefore pad it (§6.1), and on contactless it can grow a response exactly when it owns the framing beneath it. What looked like a hardware limit was an ownership boundary.

The same extension motivated a seventh response mode, splice: overwrite a run of bytes at a given offset and leave the length exactly as the card sent it. A resizing edit shifts every byte after it and, inside a signed template, invalidates far more than intended; a length-preserving splice changes one field in place and is the safe primitive for probing a value without disturbing its container. It refuses an offset or patch that would run past the end of the value rather than silently resizing — the same discipline as the modes it joins.

6.4  Below the APDU layer: activation and the ATR

Everything above assumes a card is already talking to a terminal. Reaching that point is the deepest instance of the same principle, and chronologically it comes first.

The contact relay is SimTrace2 [10]. A bank card sits in a PC/SC reader on the host; simtrace2-remsim forwards every command over USB to a SimTrace2 board running its card-emulation application, and the board impersonates the card to the terminal down to the electrical layer — supply, clock, reset and a single half-duplex line. From that platform this work inherits the parts that are hard and already correct: the activation state machine, driven entirely by interrupts as the terminal walks the electrical sequence, and the framed USB message plane that carries commands, responses and status between host and board.

What EMV additionally demands is a different protocol and a different answer-to-reset. SimTrace2's emulation was built for SIM cards, which speak the byte-oriented protocol T=0; a large share of bank cards speak only the block-oriented T=1. A bank card's ATR also encodes a clock rate, a guard time and block parameters it expects to be honoured, and an EMV terminal applies admission rules of its own on top of ISO/IEC 7816‑3, turning a card down before a single command is exchanged if the ATR falls outside them.

Two additions close that gap. The first is a complete T=1 block layer in the firmware: framing under either error-detection code, the three block types, sequence numbering, chaining in both directions, information-field-size negotiation, and the resynchronise, abort and waiting-extension service blocks. It is free-standing, depending on nothing but the C string library and its own header, which is why it survived a rebase of the whole firmware onto a newer upstream release without an edit, and why it can be exercised on a workstation with no board attached. The second is in the host tool, and is the more interesting of the two.

The ATR rewrite

The second addition is the smaller of the two. The card's real ATR is read over the reader and forwarded to the terminal, but not verbatim, because the emulation runs at exactly one set of transmission parameters. Any interface byte that asks the terminal to clock differently is a promise the board cannot keep — forward the clock-rate byte and the terminal clocks four times faster than the board can answer, and it sees framing errors rather than a card.

So the rewrite drops every byte that is an electrical promise and keeps every byte that is a protocol parameter or an identity. The historical bytes pass through untouched, so the terminal still sees the real card. The information-field size and the block-timing pair are kept, because they are protocol rather than electrical — and because EMV requires the timing pair and rejects the card outright when it is absent, falling back to an ISO default that sits outside the range EMV accepts. The protocol-indicator chain is rebuilt so those two bytes land in the group where a T=1 link is allowed to name them, and the checksum is recomputed over the new body (Fig. 6).

The same principle applies here, one layer below the APDUs. §6.1 preserves a length the terminal negotiated; §6.3 preserves a frame the chip can carry; here the rewrite preserves the terminal's electrical expectations and the card's identity while discarding what the relay cannot honour. In each case the edit is chosen so that the receiver reaches its policy rather than its parser — and the deeper the layer the tester owns, the more of the transaction becomes reachable, which is the generalisation §6.3 reaches from the other direction.

Protocol selection is treated the same way. A proposal for a protocol the ATR did not offer leaves the card mute, as the standard requires, rather than being echoed back unchecked; the terminal then falls back or resets. And because the two links are independent protocol domains, joined only at APDU level, the protocols on either side need not match: a T=1 card can be presented to a T=0 terminal and the reverse, with the host converting the response forms between them.

7The cross-layer bridge (P2, P3)

7.1  DE55 and the cross-layer check

The host half of ATRIUM decodes ISO 8583 authorisation traffic. Its integration with the card half is a single observation: DE55 carries ICC data as BER‑TLV, the same encoding a card emits, so the TLV core that parses a READ RECORD response parses DE55 unchanged. Every mutation primitive that works on a card response works on DE55 without modification.

That makes the check small enough to state completely. For each quantity that appears twice — the amount as DE4 and as tag 9F02, the currency as DE49 and as 5F2A — the checker normalises the two encodings and reports a discrepancy record naming both copies. A summary function extracts the authorisation-relevant tags (9F26 cryptogram, 9F27 CID, 9F36 ATC, 9F34 CVM results, 95 TVR) for the session log.

The interpretation is conservative and is stated in the code: a mismatch is not automatically a vulnerability — it is the signal worth chasing. A gateway may legitimately restate an amount after currency conversion. What the check establishes is that a downstream system is deciding on a number the cardholder's card never signed, and the finding is then about which copy that system trusts.

Sharing a core across two packages creates a duplication hazard: the host package vendors the TLV implementation so it can run without pyscard installed. Rather than accept drift, a parity test runs both implementations over a shared corpus — including malformed and truncated inputs — and fails the build on any divergence. The guard is documented as temporary: when a third consumer appears, both copies collapse into a shared module and the test retires with them.

7.2  Dialects as data, and inferring them

"ISO 8583" is a family. Deployments differ on message-length-indicator width and inclusiveness, presence of a TPDU header, body character encoding (ASCII or EBCDIC), MTI encoding, bitmap representation, numeric encoding, length-prefix encoding, and odd-digit padding direction — eight independent axes, each with real deployments on both sides (Table II).

Hard-coding any of them is what makes host tooling single-target. ATRIUM's codec contains no dialect-specific logic at all: a dialect is a YAML file, and an extends: mechanism keeps a new one to a short diff, because most real deployments are ISO 8583:1987 plus a handful of private-use fields.

Scheme specifications are not shipped. They are confidential, and a reconstruction from public knowledge would be wrong in ways an operator would discover mid-engagement — worse than having nothing. On a real engagement the authoritative interface specification comes from the target's owner, which is precisely why dialects must be user-authorable.

That leaves the practical question of walking into an environment without one. ATRIUM answers it by inference: a correct configuration is strongly self-verifying. The length indicator predicts exactly where the message ends; the MTI is four decimal digits of a plausible class; the bitmap names fields the dialect defines; and decoding those fields lands precisely on the final byte. Wrong configurations rarely satisfy all four. The scorer weights these so that consuming the message exactly dominates, and a syntactically valid MTI alone — which random bytes produce roughly once in three hundred — counts for almost nothing.

Two properties of the scorer are unusual in tooling of this kind. First, nothing scores a perfect 1.0: two dialects differing only in private-use fields genuinely are indistinguishable from a plain message, and the score says so rather than pretending otherwise. Second, the decoder degrades instead of raising — a message decoded up to field 43 is real evidence about an unknown link, while an exception is not. Callers inspect Message.problems and Message.complete.

7.3  An escalation ladder, with the costs declared

The host half is not one tool but four, and they are ordered by how much they can disturb the system under test (Fig. 7). Each rung buys a capability by surrendering a safety property the rung below it holds. Stating that surrender explicitly — in the code, in the tests, and to the operator — is what makes the ladder safe to put in someone else's test environment.

Rung 1 — observe, byte-exactly

The passive proxy forwards bytes exactly as received, the instant they arrive, before anything tries to understand them. Decoding gets its own copy and sits entirely off the relay path. The reasoning is the same one that produced the degrading decoder: a dialect is a guess about somebody else's system, and here a wrong guess must degrade to "I could not read that" rather than to a corrupted link. When framing itself turns out to be wrong the connection drops to opaque relay — bytes keep flowing, decoding stops, the operator is told.

That guarantee is not a claim in a comment; it is pinned by a test that runs the proxy under a deliberately wrong dialect and asserts the far side received the original bytes. A tool that observes a production-adjacent link needs exactly that kind of proof, and it is cheap to state and easy to lose.

Rung 2 — rewrite, and admit what that costs

The mutating proxy gives the guarantee up, because rewriting a message means re-encoding it from the decoded form, and a codec bug can now corrupt a live link. Three rules contain the blast radius rather than pretending it away. A message that did not decode cleanly is never mutated, since problems or trailing bytes mean the dialect is not a perfect fit and re-encoding would silently drop what was not understood. A message no rule touched is forwarded verbatim, never round-tripped, so untargeted traffic keeps rung 1's guarantee in full. And a re-encode that fails forwards the original and says so loudly — a failed mutation is a bad experiment, a broken link is a bad afternoon.

The mutation vocabulary is the card layer's: the same six modes, the same playbook shape, the same specs-loaded-from-YAML structure, with message type and direction of travel replacing the instruction byte as the gate. Two target kinds are addressed — data elements, and DE55 tags through the shared TLV core. One shipped playbook describes itself as the direct counterpart of a card-side combination, one layer up, in the same vocabulary. That is P2 and P3 paying out together: what an operator learns on one half transfers to the other.

Two modes are refused rather than guessed at. Bit-flipping and XOR are byte operations, and on a text field there is no defined answer to which bytes — the ASCII, the BCD packing, or the digits — so the engine declines instead of picking one.

Rung 3 — originate, with no acquirer present

Replay drives messages from a captured corpus at a host directly, playing the acquirer itself. This is why rung 1 keeps raw bytes: a decoded-only capture is only as good as the dialect you had at the time.

Its two modes are an experiment design rather than a feature list. Verbatim resends exactly what was captured; most hosts should decline it, because the trace and reference numbers have been seen before — and a host that approves a byte-identical replay has no duplicate detection at all. Nothing clever is needed to ask that question, which is why it is the default. Freshen rewrites only the volatile routing fields — trace number, retrieval reference, transmission and local date-time — so the message looks like a new transaction, while leaving DE55 and its cryptogram exactly as captured. That asks the sharper question: is the cryptogram actually bound to those fields, or can a genuine one be reused under a new trace number? DE55 is untouched by design; reusing it untouched is the experiment.

Replay is the most active thing in the toolkit — it originates transactions rather than observing someone else's — so the scoping guard of §11.2 applies in full, and the cardholder-data check matters more here than anywhere else: a corpus captured from a live link would otherwise resend real cardholder data.

7.4  Cryptographic closure

The final rung answers the question the check could previously only pose. Given an issuer master key, ATRIUM derives the card's unique derived key from the PAN and sequence number, derives the session key from the transaction counter, and recomputes the cryptogram over the message as captured.

Three design choices make this an instrument rather than a calculator.

The data composition is a profile, not a constant. The MAC itself is fixed by the standard; what varies between schemes is which bytes get MACed, and that is precisely the part the scheme specifications keep confidential. So the composition is an ordered list of tags in a YAML file — the same treatment dialects get, for the same reason. The recommended specification-order composition ships; a scheme-specific one is a short file the operator writes from the document their client hands them.

Verification refuses to guess. A cryptogram computed over the wrong data fails identically to a forged one, and telling those two apart is the entire value of the exercise. Missing tags are therefore reported rather than skipped or zero-filled, and the verifier declines to compute at all when its inputs are incomplete, returning a stated reason instead of a mismatch it cannot stand behind. The comparison is constant-time on principle — this code runs beside code that talks to a host, and a verifier that leaks its comparison sets a bad example.

Cross-layer fallback is reported, never silent. When DE55 omits a tag that also exists as a data element — the amount, the currency — the builder may fall back to the 8583 copy, and records that it did. This is the thesis in a single mechanism: if the two copies disagree, verification fails, and the operator learns which copy the card actually signed. Silently substituting would produce a mismatch with no explanation; reporting the substitution turns the same failure into evidence.

Re-signing completes the loop for rung 3. With a valid cryptogram over the new counter and amount, an approval no longer merely tells you the host skipped cryptogram checking — it tells you what the host does or does not enforce besides the cryptogram. Issuer response cryptograms are generated by both defined methods, so the response leg can be exercised too.

Cryptography came last, and the ordering matters: everything above it answers real questions without a single key. A playbook that tampers with a cryptogram asks whether the value is verified at all — which is worth knowing before investing in computing one correctly.

8Evidence that accumulates (P4)

8.1  A fingerprint that is not an identity

Every session begins with a structured profile of the card: application identifiers enumerated via the directory or a fallback list, the full record map per application, PDOL and CDOL layouts, decoded AIP flags, every CVM rule with its method and condition, derived cryptographic capability, and counters obtained by GET DATA.

From that profile ATRIUM derives a fingerprint: a SHA-256 digest, truncated, over the sorted list of application identifier, AIP and decoded capability flags — and nothing else.

The exclusions are the design. The fingerprint contains no primary account number, no track data, no expiry, no cardholder name. It is therefore not a card identity but a capability class: two cards issued on the same product profile hash identically, and the store's knowledge generalises to the next specimen of that product rather than being stranded on the one in the reader. The same choice makes the accumulated corpus something an operator can retain and share without holding cardholder data — a research asset instead of a liability.

8.2  Turning status words into evidence

During a relay session, every command/response pair is paired and streamed to the console, and every status word is classified. Routine outcomes are discarded: 9000, and the 61 XX/6C XX chaining and length-correction codes, carry no signal and would swamp the store. Five codes are labelled security_condition — 6983, 6984, 6985, 6986, 6988 — because each means the card evaluated something and refused. Other 6xxx codes are labelled interesting. The operator can also mark any row manually from the live trace, and manual marks are ranked above automatic ones because a human decided they mattered.

Each record carries the fingerprint, the session, the command's instruction byte, both APDUs and the label. That last detail — storing the instruction byte alongside the status word — is what makes the corpus useful: 6985 on GENERATE AC and 6985 on GPO mean entirely different things, and the pair is the unit of inference.

8.3  From evidence to the next experiment

Two consumers read the store. The first is a deterministic recommender that ranks up to five next attacks from card profile, attack history and outcome patterns. Partially successful attacks rank first, then outcome-derived adjustments, then attacks whose preconditions the profile satisfies, then combination prerequisites, then the untried remainder. The outcome-derived rules encode exactly the reasoning an experienced operator applies: 6985 or 6984 on GENERATE AC means the card caught the manipulation, so downgrade authentication before retrying verification; 6985 on GPO means the PDOL edit was rejected, so change the vector; three or more security conditions means the card is sensitive, so baseline with silent collection first; 6983 on VERIFY means the PIN path is closed, so pursue no-CVM directly.

The second consumer is an optional LLM agent with eleven tools — fingerprint, configure, start and stop the relay, read the mutation and session logs, load and record card intelligence, query outcome patterns. It is provider-agnostic: Anthropic, OpenAI, or any OpenAI-compatible local server, resolved from environment with an explicit override, and the platform reports the agent as unavailable and carries on when none is configured.

On what the model is for

The agent does not invent byte sequences. The search space is made explicit before the model sees it — eleven attack templates with stated preconditions, a structured card profile, and a labelled outcome history — so the model's job is selection and interpretation, which is what it is good at, rather than protocol synthesis, which it is not. The deterministic recommender remains the floor: every conclusion the agent reaches is reproducible without it.

A cross-card query completes the loop. Before a never-before-seen card, an operator can ask what status-word patterns have appeared across every card previously tested and on how many distinct fingerprints — a prior, derived from evidence, for a specimen about which nothing else is yet known.

9Communication: separating the card from the rig

The relay's transport abstraction admits a card that is not in the room. This matters for three reasons: laboratories share scarce specimens; an authorised engagement may span jurisdictions; and relay-resistance behaviour is only meaningfully studied at realistic network latency.

Publishing a payment card on a socket is, however, precisely the operation that must not be casual. ATRIUM's link uses an SSH-shaped trust model rather than a web-shaped one. The card host generates a long-lived self-signed identity once and prints a pairing string carrying its address, its certificate fingerprint and an access token. The rig operator transfers that string out of band and pastes it.

Authentication is then mutual and ordered. The rig authenticates the card host by pinning the certificate's SHA-256 against the fingerprint in the pairing string; the card host authenticates the rig by a token compared in constant time. The token is transmitted only after the pin matches, so an impostor presenting a substituted certificate never receives it.

There is no domain to validate, and involving a public certificate authority would make any CA-issued certificate acceptable — strictly weaker than pinning one known key. The reasoning is the same as an SSH host key: trust is established out of band by two operators who know each other.

Two operational properties follow. Serving a card on a non-loopback address without the secure mode is refused outright, so a card cannot be published in the clear by accident; plaintext remains available over loopback for SSH-tunnelled use and the console labels it plaintext — tunnel only so the weaker mode is never invisible. And because the pairing string carries the token, it is treated as a private key: a single rotation command generates a fresh identity and invalidates every string previously issued, which is the operation a collaboration's end actually requires.

The report is explicit about the limit of this: transport security protects the link, not the endpoints. Both operators still need authorisation for the card and the terminal being tested.

9.1  The other direction: presenting a card to a terminal

Everything above concerns reaching a card. The contactless work adds the mirror capability — reaching a terminal, by having the platform itself act as the card. Put into target mode, the PN532 inside the ACR122U stops looking for cards and starts answering as one; a terminal in whose field it sits selects it and sends APDUs, which the emulator forwards to whatever CardTransport the operator chose. This is the contactless counterpart of what the relay board does on the contact side, and it composes with every card source: the terminal can be made to talk to a physical card in another reader, a card across the network, or a recorded capture.

The limits of this half matter as much as its capabilities, and they are stated where an operator will read them before trusting a result. One is genuinely the chip's: in target mode the PN532 forces the first UID byte to the random-UID marker, so a terminal that pins a specific card UID will not see the card's own, and no amount of software changes that.

Two others were reported in earlier revisions of this report as hardware facts, and that was too pessimistic. While the chip performs ISO-DEP, one response must fit one frame and the frame waiting time is the firmware's — so a long response is refused rather than truncated, and a relay that outruns the budget is dropped by the terminal with nothing said. Both are consequences of letting the chip own the block layer. A second driver takes that layer over and answers RATS with an ATS of the platform's own composition: the waiting budget becomes one the platform chose, S(WTX) asks the terminal for more time while the relayed card is still being waited on, and a long response is chained across several blocks (§6.3).

What remains true under either driver is that relaying costs time that a local card does not. Every APDU is a USB round trip — and, over the Android path, a network round trip as well — so an EMV contactless kernel's transaction budget can still be lost, and a mutation rule that injects extra commands spends that budget twice. Owning the block layer buys room to negotiate rather than exemption. None of this has been exercised against a real terminal; the block arithmetic and relay logic are covered against a fake chip, and the RF behaviour is not and cannot be.

10Worked examples

10.1  Decoupling a cryptogram from its amount

The clearest demonstration of the cross-layer check combines a command-side edit with a structural one. The PDOL amount is set to one cent, which is what the card is told and what the CVM threshold rules are evaluated against; simultaneously, the amount is removed from CDOL1, so the cryptogram is not bound to any amount at all. The terminal displays and forwards the genuine amount throughout.

Listing 1 — the mutation spec, verbatim from a shipped playbook
# PDOL: what the card is told it is worth
pdol_mutations:
  - tag:     "9F02"          # Amount, Authorised
    value:   "000000000001"  # one cent
    enabled: true
  - tag:     "5F2A"          # keep it coherent
    value:   "0978"
    enabled: true

# CDOL1: what the cryptogram is allowed to cover
dol_mutations:
  - target_tag: "8C"         # CDOL1
    mode:       remove_field
    field_tag:  "9F02"
    enabled:    true
    comment:    "AC not bound to amount"

Three mechanisms have to cooperate for that to reach the card's decision logic. The CDOL edit shortens a READ RECORD response, so §6.1 restores the negotiated length. The terminal then packs a GENERATE AC one field lighter, so §6.2 re-packs it into the layout the card declared, zero-filling the amount. Only then does the card compute a cryptogram — over a transaction description in which the amount is zero.

The result is a completed, conformant transaction in which the terminal's belief about the amount and the cryptogram's coverage of it have been severed. Whether that is exploitable is not a card-layer question, which is the point: it is answered one layer up.

10.2  Catching it at the switch

The host layer decodes the resulting authorisation and asks the only question that matters. The check is three lines of operator code and reports both copies of the disputed quantity.

Listing 2 — the cross-layer check
from host.iso8583 import (
    de55, load_dialect, unpack)

msg, _ = unpack(load_dialect("base24"), captured)
nodes  = de55.from_message(msg)

print(de55.summary(nodes))
# {'9F26': '4C8B...', '9F27': '80',
#  '9F36': '015A', '9F34': '1F0302',
#  '95': '0000000000'}

for d in de55.cross_check(msg):
    print(d)
# amount mismatch:
#   DE4=000000012000
#   but tag 9F02=000000000001

That single line of output is the finding, and the full picture is worse than it reads. Three copies of one quantity now disagree: the switch routes and authorises 120.00 from DE4; the ICC data it forwards says one cent; and the cryptogram covers neither, because the amount was removed from the object list that defines its scope. The CVM results byte in the same message reports a verification that was evaluated against the cent.

10.3  Determining which copy was signed

Until the platform could derive keys, the previous paragraph ended in an open question. It no longer does. Given the issuer master key for the test range, the verifier derives the card's key from the PAN, derives the session key from the counter, and recomputes the cryptogram over the message as captured.

Listing 3 — completing the check
from host.crypto import (
    derive_udk, load_profile, verify_cryptogram)

card = derive_udk(imk, pan="4111111111111111")
res  = verify_cryptogram(
    msg, card.udk, load_profile("emv-book2"))

print(res)
# ARQC MISMATCH (ATC 015A):
#   found 4C8B..., computed 91D2...

print(res.data.substituted,
      res.data.used["9F02"])
# ('9F02',)  000000012000
#  ^ DE55 carried no 9F02, so DE4's copy
#    was used — and it does not verify.
#    The card did not sign the amount
#    the switch is authorising.

The substitution report is what makes that readable. The builder needed tag 9F02, DE55 did not carry one, so the 8583 copy was used as a fallback — and the result does not verify. Had the card signed the routed amount, it would have. The mismatch plus the substitution record together identify which copy carries the card's signature, which is exactly the question §3 defined divergence around.

The report is careful about what this does not prove. A mismatch is not by itself evidence of forgery: a wrong profile, a wrong key or a missing tag produces an identical failure, and the result object carries enough context to tell those apart. The self-test reports the same limit: it checks that derivation, MACing and response-cryptogram generation are self-consistent and correctly diversified, and then states plainly that it has not checked any profile against a particular scheme's composition, because that composition is confidential and ships only as an editable file. Validate against the target's own test vectors before a verification result goes into a report.

10.4  Asking whether the cryptogram is bound to anything

The sharpest host-layer experiment needs no key at all. Take a captured authorisation, rewrite only the volatile routing fields so it looks like a fresh transaction, and leave DE55 exactly as it was — a genuine cryptogram, over a genuine counter, reused under a new trace number.

An approval is then a finding on its own terms: the host accepted a cryptogram that is not bound to the transaction identity it just authorised. A decline is equally informative and much cheaper to obtain than the alternative, which is why verbatim replay — where most hosts should decline on duplicate detection alone — is the default rather than the interesting mode. The report classifies responses, counts them by code, and states its verdict as a lead to verify rather than a conclusion, on the grounds that approval codes are scheme-specific and a certification host may be configured to approve everything.

Re-signing turns the same corpus into a different question. With the cryptogram recomputed over the new counter and amount, an approval no longer tells you the host skipped cryptogram checking; it tells you what that host enforces besides the cryptogram.

Before any of that, an engagement usually starts without an interface specification. Capture first, then let the bytes decide.

10.6  The second session on the same product

Finally, the property that only appears over time. In session one, a verification-bypass attempt draws 6985 from GENERATE AC: the card evaluated the manipulation and refused. The label, the instruction byte and the fingerprint are stored.

In session two — the same card, or a different card of the same product, on a different bench — the recommender reads that pattern before anything is armed and reorders its output: authentication downgrade and AFL manipulation rank above the verification attack that previously failed, because the recorded refusal is evidence about this capability class, not about that afternoon. An operator who has never seen the card inherits the reasoning of one who has.

This is P4 in one paragraph: nothing here is a new attack, but the sequence in which attacks are attempted is now derived from evidence rather than from habit, and it improves as the corpus grows.

11Safety posture, and its inversion

An instrument that drives a payment card and can start privileged helpers is itself a target. ATRIUM's own hardening is part of the contribution, because the failure mode it avoids is one this class of tool routinely exhibits.

11.1  The card layer: let nothing reach in

The console binds loopback by default, and refuses to bind any other address unless a shared token is configured — there is no login, so widening the bind without authentication would publish a card relay to the network. A Host-header allow-list defeats DNS rebinding, where a malicious page re-resolves its own domain to 127.0.0.1 and is thereby treated as same-origin; the request still arrives carrying the attacker's name, and is answered 421.

The most consequential decision concerns privilege. The relay board's daemon needs raw USB access, which needs root. The two ways to obtain that from an HTTP handler are a password prompt with nobody present to answer it, or a passwordless sudo rule that quietly converts the API into a root shell for anything that reaches the port. ATRIUM does neither: it launches no subprocess at all. The operator runs the daemon in their own terminal, and the platform detects it by reading /proc, which requires no privilege.

Because that guarantee is easy to erode later with one convenient commit, it is enforced mechanically: a test walks the module's abstract syntax tree and fails the build if an execution call ever reappears there. A comment mentioning subprocess does not trip it; a call does. The invariant is a property of the repository, not of anyone's memory.

11.2  The host layer: constrain what reaches out

The host half inverts the posture, and naming that inversion is the design point. The card-side tool is hardened so that nothing reaches in. A host-side tool reaches out by design — it opens sockets toward an acquirer or a switch — so its hardening is the mirror image, and it arrived in the same commit as the first socket rather than after it.

Two rules do the work. A target allow-list means the proxy refuses to connect anywhere that was not named up front, and it fails closed in the strongest sense: an empty allow-list permits nothing at all, so the tool cannot transmit until an operator has named a target explicitly. A typo in a hostname is then a refusal rather than a tunnel into something that was never in scope. Test-PAN awareness means an account number outside the configured ranges is the loudest available signal that the link is pointed at production. The check is unconditional; what is configurable is the response, which defaults to warning loudly and can be set to abort. The default is a warning, not a refusal: a false positive that halts a live engagement teaches operators to disable the guard, which is a worse outcome than one that shouts. Well-known documentation test ranges ship as a convenience, with the accompanying note that they are not a substitute for the target's own ranges — which, like the interface specification, come from the host's owner.

Masking is handled separately and earlier, because policy is not a data-protection control. Account numbers and track data are masked at the point of capture, not on the way out, so the decoded view never holds them in full regardless of what any policy says. The documentation is equally direct about the limit of that: raw wire bytes are retained deliberately — the corpus everything downstream depends on — and the wire carries the account number in the clear. A capture file therefore is cardholder data, is excluded from version control, and can be dropped entirely at the cost of replay and re-decoding. Masking protects the at-a-glance view, not the file, and saying so is worth more than a reassuring sentence.

11.3  Ethics and dual use

ATRIUM mints nothing, clones nothing, and recovers no key. Its card-layer half manipulates a session involving a physically present card in a reader the operator controls, which is a meaningful boundary. Its host-layer half is bounded by configuration rather than by physics (§3.2), and a tool which originates authorisation messages is only as safe as the scope it is pointed at — which is why that scope is enforced by the code, declared to the operator, and covered by its own test suite rather than left to discipline.

The cryptographic layer deserves the same directness. It derives keys from an issuer master key the operator must already possess; it does not recover one, and no capability here brings an operator closer to a key they were not given. Verification is the useful direction — establishing whether what is in a capture was really signed by the card it claims to come from — and re-signing exists so that a replay experiment asks a sharper question, not so that a fabricated transaction looks genuine to a system the operator has no authorisation to touch.

Four commitments follow. Scheme interface specifications and cryptogram compositions are not shipped, reconstructed or inferred. The card-side evidence store holds no cardholder data by construction (§8.1), and host-side captures are treated as cardholder data because the wire carries it in clear (§11.2). The cardholder-data check is always on, and the target guard fails closed. And findings belong to the parties who can fix them — the issuer, the acquirer, the terminal vendor — through coordinated disclosure, which is the only use of this instrument the authors endorse.

12Evaluation

We evaluate the artifact along three axes and are explicit about the fourth, which is not yet done.

12.1  Implementation

The platform is 28,905 lines of Python with no runtime dependency beyond the smart-card, web and DES stacks. On the card side the mutation engine (1,833 lines), structured logger, fingerprinter and agent carry most of the weight, with the intelligence store and the secure link behind them. The contactless subsystem adds roughly 3,400 lines across the PN532 protocol, the ACR122U link, the ISO-DEP block layer, two card-emulation drivers, the contactless, recorded and NFCGate transports, and centralised reader discovery. The host package is about 4,600 lines excluding its tests — replay, the operator CLI, the mutation engine, the proxies, the codec, capture, cryptogram handling and the scoping guard — and ships three dialects, six playbooks and three cryptogram profiles as data.

12.2  Correctness validation

787 automated tests pass on Python 3.11 and 3.12 in continuous integration (Table V). The distribution is uneven: the largest suites test the contactless protocol handling, the mutation engine and the platform's own control plane — remote-execution prevention, path traversal, DNS rebinding, bind guards, token enforcement, graceful degradation with no model configured — because those are the code with the highest consequence of failure and the lowest visibility during normal use. The thirteen tests that exercise the contactless drivers require the smart-card library to import and so run in CI while being skipped on a bare checkout; every other test runs everywhere, hardware or not.

Four suites test properties rather than behaviour. The parity suite runs both TLV implementations over a shared corpus and fails on divergence, keeping a known duplication in step (§7.1). The security suite's AST walk fails the build on a reintroduced execution call (§11.1). The proxy suite runs the passive relay under a deliberately wrong dialect and asserts the far side received the original bytes, which is the only way rung 1's guarantee stays true (§7.3). And the codec's central fixture is assembled from explicit bytes rather than produced by the packer, so a symmetric bug — one that encodes and decodes wrongly in the same direction — cannot pass.

One negative result belongs here, because it cost the most. Three defects stood between a card that activated and a transaction that completed, all three in the extension of §6.4 rather than in the platform beneath it: an ATR the terminal refused outright, responses discarded inside the firmware without a log, and chunks colliding with the reader on a half-duplex line. Two of the three are the characteristic hazard of adding a state to a mature system — a new protocol path that an older enumeration elsewhere in the firmware did not know to admit. Through all of it the block-layer suite stayed green, because it entered through doors the firmware does not use: the harness enqueued directly onto the transmit queue, past the readiness check the real dispatcher applies, and its chaining test fed one chunk per turn, which is not how the host behaves. A suite can be thorough about a component and still test a path that does not exist in the assembled system. Both entry points are now the dispatcher's own, and a test queues a whole response up front and asserts the card stays silent until the reader asks for the next block.

The cryptographic suite is joined by a self-test the operator can run, which is unusual in being explicit about its own limits: it establishes that the DES primitive matches a reference implementation and that derivation, MACing and response-cryptogram generation are self-consistent and correctly diversified — and then states that it has not established that any profile matches a particular scheme's composition, because that is confidential and ships only as an editable file.

12.3  Expressiveness

Against the four properties: P1 is met for the shrinking-mutation class on contact — four of eleven card templates depend on it, and none is runnable on T=0 without it — and now on contactless too, where the same fidelity concern points the other way and is answered by declining an oversized mutation rather than corrupting the frame (§6.3). P2 is met at both layers and now extends past protocol structure into cryptography: dialects, mutation playbooks and the data composition a cryptogram covers are all files. P3 is met, guarded by the parity suite, and demonstrated rather than asserted — a host playbook and a card combination express the same attack one layer apart in the same vocabulary (Table IV). P4 is met at the card layer and remains the property with no analogue in the tooling surveyed in Table I; the host layer's capture corpus is its counterpart, though it is not yet keyed for cross-engagement inference the way the card store is.

12.4  What is not evaluated here

The contact relay is the part of the platform with results on hardware, and three configurations are confirmed [15]. A complete EMV transaction runs over native T=1 with the card's own rewritten ATR: application selection, processing options, record reads and both cryptogram exchanges, through to a card decision — the card returns a cryptogram asking to go online, the terminal finds no acquirer and asks again, and the card declines. That is what the same card does inserted directly into the same terminal; reaching a decision is the success condition, not the decision itself. A T=0 card also relays end to end, including the status-word chaining that makes the terminal issue a follow-up read. And a T=1 card can be presented behind a T=0 face, the host converting the response forms as it goes.

One detail of that transaction is evidence for §6.4. Both cryptogram commands — 35 and 45 bytes — crossed as single blocks, which is only possible if the terminal is acting on the information-field size the rewritten ATR advertises. The rewrite is not merely accepted; it is being read and honoured. The same fact is why reader-to-card chaining remains unexercised: at that advertised size no ordinary EMV command needs it.

What this is not is a population study. It is one card and one terminal per configuration, which establishes that the relay path works and says nothing about how any product behaves.

No empirical study against a population of cards, terminals or switches is reported. Such a study requires authorised access to each device under test, and its results are engagement-confidential in most of the settings where it can be run. We state this plainly rather than substituting anecdote: the claims in this report are about what the instrument makes testable, not about what any deployed product does.

Three specific gaps follow from the newest work. The ISO-DEP driver and the Android transport are the least exercised code in the platform: both are covered only against fakes, and both make claims — that a terminal will grant a waiting extension, that a phone's stack will relay an APDU inside the budget — that only hardware can settle. No cryptogram profile here has been validated against a scheme's own test vectors, so a verification result is a lead requiring confirmation rather than a finding — the platform says so itself. And the replay verdicts have been exercised against test doubles, not certification hosts, so their calibration against real approval behaviour is unmeasured. A protocol for a multi-card, multi-host study — capability-class sampling, per-template precondition filtering, outcome labelling as the dependent variable — is the natural next publication, and the fingerprint scheme of §8.1 was designed to make its results poolable across sites without pooling cardholder data.

13Limitations and roadmap

Contactless is real, and its bounds have moved. The relay reaches the contactless interface as well as contact, which closes what earlier revisions called the single largest scope gap. Two of the three limits those revisions reported as hardware facts turned out to be consequences of letting the chip own the block layer, and taking that layer over retires them (§6.3) — an instructive correction, and a reminder that a limit attributed to hardware deserves a second look before it is written down. What remains: only one reader is supported, the ACR122U; the chip's forced random UID is genuinely out of reach in emulation; and relaying still costs time an EMV kernel's budget may not allow, which S(WTX) can negotiate but not abolish. The chip-managed driver stays the default, so an operator who does not switch still meets the old ceiling. None of this has been exercised against real terminals from the machine that wrote it; the block arithmetic and relay logic are covered against a fake chip, the radio behaviour is not and cannot be without hardware.

The relay layer's error paths are unexercised. The relay keeps its own ledger of this [15], and it is short. The block layer's recovery machinery — resynchronise, abort, error-detection failure — and reader-to-card chaining have only ever run in unit tests, because with the information-field size advertised at its maximum no ordinary EMV command needs chaining and no real exchange has yet produced an error. Two smaller gaps tend to surface as a mystery: the waiting-time extension is implemented and tested but unreachable on the block-protocol path, so a card slower than the terminal's budget is abandoned rather than granted more time; and the block layer borrows the byte-protocol waiting-time counter instead of deriving its own from the ATR. The contactless side gained exactly this negotiation (§6.3) while the contact side still lacks it.

Profiles are unvalidated against scheme vectors. The cryptographic layer computes correctly against itself and against a reference DES implementation, but no shipped composition profile has been checked against a scheme's own test vectors — because those compositions are confidential and are not reconstructed here. A verification result is therefore a lead requiring confirmation against material the target's owner supplies, and the platform's self-test says exactly that rather than letting a green run imply more.

Mutation surrenders byte-exactness. Rung 2 of the ladder can, in principle, corrupt a live link: a codec defect now reaches the wire. The three containment rules confine the exposure to messages a rule actually targeted, and untargeted traffic keeps the full passive guarantee — but the exposure is real, it is the price of the capability, and the recommendation stands: if you do not need to change anything, use the passive proxy.

Fingerprint coarseness. Keying on application identity and capability flags is intentional (§8.1) but coarse: two products with identical capability profiles collide, and a card whose profile changes after issuer scripting will hash differently. Both behaviours are correct for a capability class and wrong for a card identity; the store is only meaningful under the former reading. The host layer has no equivalent key at all — its corpus is per-engagement, so cross-engagement inference is a card-side capability only.

Agent dependence. The agent requires a tool-calling model, and a model that silently ignores tools produces a stalled loop rather than a wrong answer — detected and reported, but still a wasted session. Every conclusion it reaches is reproducible through the deterministic recommender, which is why the agent is optional throughout. It also has no host-layer tools: the ladder is operator-driven.

13.1  What is next

All five originally planned phases are complete, so the remaining work is narrower and mostly consists of finishing symmetries the current design implies but does not yet deliver.

  1. Re-signing on the live path. Replay can recompute a cryptogram over a message it has changed; the mutating proxy cannot. Until it can, a live mutation that touches covered data is detectable by any host that verifies — which is sometimes the experiment, and sometimes an accident.
  2. The second key-derivation option, for cards whose account and sequence numbers do not fit the direct method.
  3. Extracting the shared core. The TLV duplication is currently held together by the parity suite; a third consumer justifies collapsing both copies into one module and retiring the guard with them.
  4. Agent tools for the host ladder, so a session can reason across the seam rather than only along the card side of it.
  5. Empirical validation of both emulation drivers against real terminals — the one part of the platform that cannot be tested without hardware, and now the part carrying the most untested new code. The chaining and S(WTX) arithmetic is covered against a fake chip; whether a given EMV kernel honours a negotiated waiting extension in practice is an open question this report cannot answer.

14Conclusion

The attacks that have mattered against chip payments were not breaks of cryptography. They were disagreements: about how much, about who was verified, about which application was running — disagreements that every individual layer considered conformant and no single layer was positioned to detect.

Tooling built one layer at a time cannot test for that, and tooling that starts each engagement empty cannot accumulate the evidence needed to know where to look. This report treats agreement between layers as the property under test, sets out the four properties an instrument needs to test for it, and describes a platform that implements all four: mutations that preserve the invariants a receiver checks before it thinks, targets described as data rather than code, one semantic core spanning the card and the authorisation message, and an evidence store keyed to what a card is rather than to whom it belongs.

With the host ladder complete, the check now completes. A divergence can be induced at the card boundary, observed as it crosses the authorisation boundary, and — given the key the operator was entrusted with — resolved: this is the copy the card actually signed. The question §3 defined has an answer procedure rather than only a definition, and the same playbook vocabulary expresses the experiment on either side of the seam.

The smallest piece of it is three bytes of padding. Three bytes of padding inside a template, inserted so a shortened response still matches a length negotiated moments earlier, are the difference between measuring a terminal's byte counter and measuring its policy. The largest piece rhymes with it: a passive proxy that forwards bytes before it tries to understand them, because a guess about someone else's protocol should degrade into silence rather than into a corrupted link. Most of what separates fault injection from noise is that kind of care — and most of what separates a research instrument from a disposable script is whether it remembers what it learned and admits what it does not know.

The contact relay is a second repository in the same toolchain: a fork of SimTrace2 [10] tracking upstream 0.8.x with the T=1 block layer and ATR rewrite of §6.4 applied on top. The board must be flashed with the card-emulation application rather than the tracing one, since on this hardware the tracing build is sniffer-only. No card reader, relay board, model API key or host link is needed for the test suite: the hardware seam is stubbed, the contactless drivers are exercised against a fake chip, the proxy and replay suites run against test doubles on loopback, and the host package imports no smart-card dependency. The thirteen tests that import the smart-card library skip on a bare checkout and run in CI, where it is installed. Continuous integration runs the same command on Python 3.11 and 3.12.

One dependency matters: the cryptographic layer needs a DES implementation, so a checkout installed without the root requirements file will see the entire cryptography suite fail on an import error rather than skip.
